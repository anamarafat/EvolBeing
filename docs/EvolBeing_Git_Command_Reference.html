How to use this reference

Commands work in Git Bash, PowerShell, and Windows CMD unless otherwise indicated. Lines beginning with # are explanatory comments in Git Bash; copy the actual git ... commands into PowerShell or CMD, not the comment lines. Replace placeholder text such as YOUR_USERNAME and feature/obj-reader.

Git tracks committed files; CMake/Ninja-generated build/ files should normally be excluded with .gitignore. GitHub is the remote host, not the same thing as Git.

1 · Initial setup (commands we used)

# Confirm Git is installed
git --version

# Set the author identity for commits on this computer
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

# Verify the identity Git will record in commits
git config --global user.name
git config --global user.email

# Initialize the current directory as a new Git repository
git init

# Show the repository root even if you're in a subdirectory
git rev-parse --show-toplevel

# Return true if the current directory is in a working tree
git rev-parse --is-inside-work-tree

Use git config user.email "..." (without --global) to override your identity only for the current repository.

Recommended .gitignore

# Save these lines in a file named .gitignore (not in the terminal)
build/

Commit any intentionally shared VS Code workspace settings separately; do not automatically ignore the entire .vscode/ folder if you want to share settings.

2 · Inspect repository state and history

# Show modified, staged, untracked files and branch state
git status

# Compact status (M = modified, ?? = untracked)
git status --short

# Show unstaged edits to tracked files
git diff

# Show changes already staged for the next commit
git diff --staged

# Compact commit history, including branch decorations
git log --oneline --graph --decorate --all

# Inspect a particular commit
git show COMMIT_HASH

# List local branches and show the current one with *
git branch

# List local and remote-tracking branches
git branch -a

3 · Stage and commit changes

# Stage all additions, modifications, and deletions under current directory
git add .

# Stage just one file
git add src/geometry/ObjReader.cpp

# Stage changes interactively in individual hunks
git add -p

# Commit staged changes with a descriptive message
git commit -m "Initial build - Gen-alpha"

# Commit all tracked-file changes without separate git add
# (does not include brand-new untracked files)
git commit -am "Fix OBJ parsing"

# Remove a file from Git tracking but keep it on disk
git rm --cached path/to/file
Good commit messages: Add OBJ mesh reader, Fix degenerate triangle handling, Report surface quality metrics. Commit logically related changes together.

4 · Connect to GitHub, push, and pull

# Set the initial local branch name to main
git branch -M main

# Link this local repo to a GitHub repo you created
git remote add origin https://github.com/YOUR_USERNAME/EvolBeing.git

# Check remote names and URLs
git remote -v

# Correct an existing origin URL if needed
git remote set-url origin https://github.com/YOUR_USERNAME/EvolBeing.git

# First push: upload main and remember its upstream branch
git push -u origin main

# Later pushes to the configured upstream
git push

# Download remote branch information without changing local files
git fetch origin

# Fetch then integrate upstream changes into current branch
git pull

# Explicitly pull main from origin
git pull origin main

# Inspect remote-tracking information
git branch -vv
Important: If the GitHub repository already has a README/initial commit, the local and remote histories may be unrelated. Do not force-push or use --allow-unrelated-histories without first checking the two histories.

5 · Branching for new features

# Create and switch to a new feature branch
git switch -c feature/obj-reader

# Switch to an existing branch
git switch main

# Create a branch without switching to it
git branch feature/mesh-metrics

# Push new feature branch and set upstream
git push -u origin feature/obj-reader

# Rename the currently checked-out branch
git branch -m feature/obj-import

# Delete a local branch already merged into current branch
git branch -d feature/obj-reader

# Delete a remote branch (after it is merged)
git push origin --delete feature/obj-reader

# Remove obsolete local remote-tracking references
git fetch --prune

Use a branch per focused change: feature/obj-reader, feature/mesh-repair, feature/metrics-report, feature/lite-gui.

6 · Merge branches

# Switch to the destination branch
git switch main

# Update main from GitHub before integrating your feature
git pull --ff-only origin main

# Merge the completed feature into main
git merge feature/obj-reader

# Upload the merged main branch
git push origin main

# Optional: force a merge commit, even when fast-forward is possible
git merge --no-ff feature/obj-reader

# Abort an in-progress merge with unresolved conflicts
git merge --abort

Merge combines branch histories and normally preserves the original commit IDs. A fast-forward merge simply advances the branch pointer when there is no divergence.

7 · Rebase a feature branch onto updated main

# Download latest GitHub changes
git fetch origin

# Switch to your feature branch
git switch feature/obj-reader

# Replay feature commits on top of latest remote main
git rebase origin/main

# If conflicts arise, edit files, then stage the resolutions
git add path/to/resolved_file.cpp

# Continue replaying commits after resolving conflicts
git rebase --continue

# Abort and return to the state before rebase
git rebase --abort

# Optional: interactively clean up your last 3 commits
git rebase -i HEAD~3
Rebase rewrites commit IDs. Prefer rebasing your own unpublished feature commits. If you've already pushed the feature branch and must update it after rebasing, git push --force-with-lease is safer than --force, but only use it on a branch you control and understand; never casually rewrite shared main.

Merge vs rebase

MergeRebase
Combines existing histories; preserves commit IDsReplays commits onto another base; changes commit IDs
Useful for integrating finished featuresUseful for updating/cleaning your own feature branch
May create a merge commitUsually produces a linear-looking history

8 · Resolve merge/rebase conflicts

# Identify conflicting files
git status

# Inspect conflict sections (or use VS Code Merge Editor)
git diff

# After editing a file to the desired final contents, stage it
git add src/geometry/ObjReader.cpp

# Finish a merge after resolving all conflicts
git commit

# OR, if you were rebasing, continue the rebase instead
git rebase --continue

# Check that the working tree is clean
git status
VS Code's Accept Current / Accept Incoming / Accept Both choices are conveniences, not automatic guarantees of correctness. Review the resulting code, compile, and run tests before completing the merge/rebase.

9 · Undo and recover safely

# Unstage a file, keeping its edits in the working directory
git restore --staged path/to/file

# Discard unstaged edits in a tracked file (DESTRUCTIVE)
git restore path/to/file

# Amend the latest commit (rewrites that commit's ID)
git commit --amend

# Make a new commit that reverses a previous commit (safe for shared history)
git revert COMMIT_HASH

# Move HEAD back one commit, keep all changes staged
git reset --soft HEAD~1

# Move HEAD back one commit, keep changes unstaged
git reset --mixed HEAD~1

# Find recent HEAD positions; useful after accidental reset/rebase
git reflog

# Preview what untracked files would be removed
git clean -nd

# Remove untracked files only after reviewing the preview
git clean -fd
Avoid without a clear recovery plan: git reset --hard, git clean -fdx, and git push --force. They can discard work or overwrite shared history.

10 · Stash, tags, and useful extras

# Temporarily save tracked modifications and staged changes
git stash push -m "WIP OBJ reader"

# Include untracked files in the stash too
git stash push -u -m "WIP geometry"

# Show saved stashes
git stash list

# Restore latest stash and remove it from stash list
git stash pop

# Apply latest stash but retain stash entry
git stash apply

# Create an annotated version tag
git tag -a gen-alpha -m "Gen-alpha baseline"

# Push this tag to GitHub
git push origin gen-alpha

# See which files Git tracks
git ls-files

# Show why a path is ignored
git check-ignore -v build/build.ninja

11 · Recommended EvolBeing workflows

A · Everyday change on an existing branch

# Review changes before saving a commit
git status
git diff

# Stage and commit
git add .
git commit -m "Improve OBJ geometry validation"

# Push to the branch's configured remote
git push

B · Start and publish a new feature

# Start from an up-to-date main branch
git switch main
git pull --ff-only origin main

# Work independently on OBJ import
git switch -c feature/obj-reader

# After writing and testing code, commit it
git add .
git commit -m "Add initial OBJ reader"

# Publish feature branch; optionally open a GitHub pull request
git push -u origin feature/obj-reader

C · Integrate a completed feature locally

# Integrate only after review/testing
git switch main
git pull --ff-only origin main
git merge feature/obj-reader
git push origin main

# Clean up the merged local branch
git branch -d feature/obj-reader

D · Recover from a merge in progress

# See whether Git is merging and which files conflict
git status

# Option 1: fix conflicts, stage files, and finish
git add .
git commit

# Option 2: cancel the merge instead
git merge --abort
Recommended habit: git status before and after operations; git diff before committing; git fetch before reviewing remote changes; build/test after resolving conflicts.
